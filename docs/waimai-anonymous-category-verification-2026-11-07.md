## 用户确认的范围

仅验证“不登录能否美团满返、比例返各自独立取两页”。不改正式查询、不接入登录、不请求第三页；失败不重试。用户已确认目前匿名混合列表只能取两页，本轮不再以“多翻混合页”为替代方案，也没有重新测试第三页限制。

## 方法与安全

- 采用现有 Node 客户端（waimai-client.node.mjs:10–36），显式 token 为空，拒绝携带 token/Authorization/cookie 的请求，仅允许配置和列表两个既有端点，拒绝重定向。
- 使用已保存查询位置；仅内存读取必要经纬度、由 cities.json 补齐城市。不输出位置、不读取 .env、本人凭证或真实结果缓存。
- 正式客户端保持不动；候选请求只对系统临时目录中的隔离副本覆盖两个过滤字段。三组各从 null 游标开始，各最多两页，仅用本组响应游标翻页。
- 共 3 次配置请求、6 次列表请求，均为成功返回两页；未触发登录要求、未请求第三页、未自动重试。页间等待约 1.2 秒。
- 原始响应、门店名称/ID、游标及动态密钥不落盘或输出。集合比较仅使用内存随机密钥 HMAC；留存证据只包含脱敏统计。

## 判断

1. **本次两组 userTypes 子集测试没有实现满返／比例返分流。**两组每页都存在相反类型，不可将其接入后称作“两类各自两页”。不据此断言平台绝无其他分类接口或参数，也不推断 userTypes 的正式含义。
2. 两组加入 meituan 的候选请求，在本次样本中仅返回美团 SKU，且各得到 40 家有效美团门店，当前基线为 32 家，净计数多 8 家。**这提供平台过滤的积极线索，不证明提升完全由该字段造成**：同时变更了 userTypes，且不同请求时刻的名单可能变化。
3. 满返候选相对基线新增12家、少4家；比例返候选新增11家、少3家。两候选间各有3家差异，不能说结果完全相同、严格包含或保证覆盖更广，更不能用合并多次查询的去重数冒充单次覆盖收益。
4. 当前正式逻辑保留原状。没有增加用户状态、登录入口、扫描页数或 APK 版本。若后续获用户确认，可单独验证只改 takeawayPlatform=meituan、保持 userTypes=[1,2,3] 的两页对照；它仍是两页混合返现类别，不是两类各两页。登录入口和会话接入继续后置。
